# 延迟调节说明（用户手册 + UI 文案来源）

> 本文是**给用户看的**，也是程序里 UI 文案的唯一来源：
> 代码里的 `app/config.py: LATENCY_KNOBS` 与本文保持一致。
> 悬浮窗/P3 的"延迟"面板直接渲染这些说明。

---

## 1. 先搞清楚：延迟是从哪来的

从"小说软件出声"到"字幕出现在屏幕上"，中间有这些环节：

```
声音 → [① 采集+重采样] → [② VAD 等你说完] → [③ 识别] → [④ 翻译] → [⑤ 画面刷新]
         ~50ms            ← 这里占大头 →       50~1500ms    100~1500ms    ~30ms
```

- **① 采集与重采样**：固定约 50 ms（重采样本身占 40 ms），**没法调，也不用管**
- **② VAD 断句等待**：**延迟的大头，且完全可调** ← 本节重点
- **③ 识别耗时**：取决于引擎与硬件
  - 流式引擎（中/英）：约 50~150 ms
  - 分块引擎（SenseVoice 日/韩/粤、Whisper 小语种）：约 300~1500 ms，模型越大越慢
- **④ 翻译**：传统 API 约 100~400 ms；LLM 首字约 200~1500 ms
- **⑤ 画面刷新**：约 30 ms，可忽略

> **关键结论**：在**分块识别**（日语、小语种）下，
> 用户真正能调、也最该调的，是 **②的"断句静音时长"**。
> 把它从 350 ms 调到 200 ms，字幕就能快 150 ms 出现，代价是句子更容易被切碎。

## 2. 一键档位

| 档位 | 断句静音 | 最长憋句 | 前后留白 | 最短语音 | 中间结果刷新 | 适合 |
|---|---|---|---|---|---|---|
| **最低延迟** | 200 ms | 4 s | 60 ms | 200 ms | 150 ms | 剧情对话快、不在乎断句零碎 |
| **平衡**（默认） | 350 ms | 8 s | 120 ms | 250 ms | 200 ms | 大多数情况 |
| **最准** | 600 ms | 15 s | 200 ms | 300 ms | 300 ms | 翻译质量优先、能忍受慢 |

参数被手动改过之后，档位会显示为 **自定义**。

---

## 3. 每个参数到底在干什么

### 3.1 断句静音时长 `min_silence_ms` —— 最重要的一个

**它在做什么**：检测到你停下来不说话之后，还要再"听"多久，才承认这句话说完了。

- **调小（如 200 ms）**：字幕更快出来。
  代价：说话人换气、思考时的自然停顿会被当成句末，
  一句话被切成好几段；翻译因此失去上下文，容易出现"每段都翻译得怪怪的"。
- **调大（如 600 ms）**：断句更完整，翻译更通顺。
  代价：字幕出现得更晚，看剧时会有明显的"跟不上"感。

**建议**：中文小说朗读通常语速平稳、停顿清晰，350 ms 就够；
日语朗读停顿更碎，可以试 250~300 ms。

### 3.2 最长憋句时间 `max_segment_ms` —— 延迟的保险丝

**它在做什么**：如果说话人一直不停（或有持续的背景音乐），不可能无限等下去，
所以设一个上限，到点强制切一刀送识别。

- **调小（如 4 s）**：连续说话时字幕更新更勤，延迟有上限。
  代价：可能正好在词中间被切断，出现半截句子。
- **调大（如 15 s）**：长句更完整。
  代价：遇到一直不停的情况，字幕可能十几秒不刷新，看起来像卡住了。

**注意**：这个参数**只在"一直没人停顿"时才生效**。
正常朗读里有停顿，起作用的始终是 3.1。

### 3.3 语音段前后留白 `speech_pad_ms`

**它在做什么**：VAD 判定的语音边界往往略微收紧，
前后各补一小段，避免句首的字（尤其爆破音、气声起头）被削掉。

- **调小（如 60 ms）**：延迟略降，但句首句尾可能缺字。
- **调大（如 200 ms）**：更完整，延迟与算力略增。

### 3.4 最短语音长度 `min_speech_ms`

**它在做什么**：太短的声音直接扔掉，不送识别。

- **调小**：更短的应答词（"嗯""对"）也能被识别，但咳嗽、键盘声、鼠标点击更容易被当成人声，
  会冒出莫名其妙的短字幕。
- **调大**：滤得更干净，但很短的对话会被吞掉。

### 3.5 中间结果刷新间隔 `partial_interval_ms`

**它在做什么**：流式引擎会边听边给"没定稿"的中间结果。
这个参数决定多久把中间结果推到画面上。

- **调小（如 100 ms）**：字幕有"实时跟读"的感觉，滚动更顺。代价：CPU 占用略增。
- **调大（如 500 ms）**：省 CPU，但字幕一跳一跳地变，观感差。

**只对流式引擎有效**（中/英）。日语/小语种走分块识别，
要等整句识别完才有结果，这个参数对它们没有效果——UI 上应对这些语言置灰并说明原因。

## 4. 不同语言的实际延迟预期

| 语言 | 引擎 | 可预期延迟 | 能否靠调节改善 |
|---|---|---|---|
| 中文 | 流式 zipformer | 约 **0.4~0.7 s** | 可，调 3.1 / 3.5 有效 |
| 英文 | 流式 zipformer | 约 0.4~0.7 s | 可 |
| **日语** | SenseVoice（分块） | 约 **1.0~1.8 s** | 只能靠调 3.1/3.2，**下限比中文高** |
| 韩语 / 粤语 | SenseVoice（分块） | 约 1.0~1.8 s | 同上 |
| 小语种 | Whisper turbo（分块） | 约 **1.5~3 s** | 同上 |

> **为什么日语天生慢**：sherpa-onnx 官方**没有日语的流式模型**
> （中文、英文、韩语都有）。所以日语只能等一整句说完再识别。
> 这不是参数没调好，是模型可用性的限制（见 `计划书.md` 12.3）。
> 若将来把 ReazonSpeech 日语流式模型转换过来，日语延迟可以降到中文同一水平。

## 5. UI 设计要求（P3 实现，此处先定稿）

延迟面板必须做到：

1. **档位按钮 + 单个滑杆并存**：先给三个预设按钮（低延迟/平衡/最准），
   下面再放开单个参数滑杆，滑杆一动档位自动变"自定义"。
2. **每个滑杆旁边直接显示上面第 3 节的说明**（不要藏在问号提示里），
   而且要**同时说清"调小会怎样"和"调大会怎样"**——
   只说"延迟相关"等于没说。
3. **实时反馈**：面板上显示当前设定下的**预估延迟**（按语言取基准值 + VAD 等待时间），
   让用户拖滑杆时立刻看到"预计快 0.2 秒 / 字幕可能被切碎"。
4. **每语言分别保存**：中文用 350 ms、日语用 250 ms 是完全合理的组合，
   配置应按语言记忆（`asr.routing` 已是按语言的结构，延迟参数也照此扩展）。
5. **非流式引擎置灰**：选日语/小语种时，`partial_interval_ms` 滑杆置灰并注明
   "该语言使用分块识别，此项无效"。
