## 1. 测试方法（为什么结论可信）

用**真实的 ASR 输出**做输入，而不是干净的例句：

```
列車?リンファンは手の中の声堂の鍵を強く握りしめ。
```

这条里有真实的识别错误（「声堂」应为「青銅」），
所以能一并验证**术语表能不能把识别错误拉回来**——这是实际使用中必然遇到的场景。

**关键前提：必须先预热。** LM Studio 按需加载模型，
第一次调用包含模型加载时间。不预热的话耗时数据全是错的（这个坑踩过两次）：

| 模型 | 不预热看着像 | 预热后真实推理 |
|---|---|---|
| sakura-galtransl-7b | 36.5s | **0.30s** |
| qwen3.8-9b | 105s | 22.7s |
| qwen3.8-27b | 159s | 34.6s |

## 3. ⚠️ 推理模型的"思考"在 API 侧关不掉

9B / 27B 返回**空译文**的原因：它们的思考 token 把 `max_tokens` 全吃光了。
实测三种"关思考"的办法**全部无效**：

| 方式 | 结果 |
|---|---|
| `chat_template_kwargs: {"enable_thinking": false}` | ❌ 仍生成 7210 字思考 |
| 消息尾部加 `/no_think` | ❌ 仍生成 7369 字思考 |
| 系统提示词里加 `/no_think` | ❌ 仍生成 6570 字思考 |
| **在 LM Studio 侧手动关闭** | ✅ 有效（completion 降到 6~13 token） |

**产品化结论**：不能假设用户会去服务端关思考。
必须处理"`content` 为空但 `reasoning_content` 非空"的情况——
我们的做法是三级降级：**批量 → 加大预算重试 → 逐条**，
最终如果仍失败就**明确报错**，绝不静默输出空白字幕。

实测降级链（故意用思考关不掉的 9B）：

```
512 tok → 空译文（2137 字思考，被截断）
  → 2048 tok 重试 → 仍空（7986 字思考）
    → 退回逐条 → 仍空
      → 明确报错："模型返回空译文（输出被 max_tokens 截断，疑为推理模型把预算用在思考上）"
```

## 4. 批量翻译省 70% token（实测）

| 方式 | 5 条字幕的 token | 耗时 |
|---|---|---|
| 逐条请求 | 1508 | 0.35s |
| **一次请求翻 5 条** | **439** | **0.24s** |

原因：逐条时每条都要重发系统提示词 + 术语表 + 前文。
**所以批量是默认行为**（`batch_size=5`，凑够就发或最多等 350ms）。

代价：批量时术语表遵守率略降（实测有一条「声堂」没被替换成「青铜」），
因此加了术语表校验 + 违规条目**单独重翻**。

## 6. ⚠️ 实测事故：sakura 把提示词原样吐回来

**现象**：换 sakura 后译文变成

```
【待翻译（共 1 条）】
请按相同编号逐条输出译文，每行一条，格式为「编号. 译文」。不要合并或省略任何一条。
```

**而且这段垃圾被写进上下文后污染了后续所有请求**，形成恶性循环，越跑越乱。

**根因**：sakura-galtransl 是**微调过的翻译模型，不是指令模型**。
喂它带【前文】【术语表】的指令式 prompt，它会把整段 prompt 当正文"翻译"。

**两层修复**：

1. **回显检测**：译文里出现我们自己的提示词标记（`【待翻译`/`【前文`/`【术语表`/
   `请按相同编号`/`硬性要求`）即判定失败——**不上屏、不进缓存、不进上下文**。
   这条防线对任何模型都有效。
2. **`prompt_style: chat | plain`**：plain 模式只把原文发给模型、不带任何指令，
   按行而非编号解析。按模型名自动识别（sakura/galtransl/opus-mt/nllb → plain），可手动覆盖。

## 7. 术语表在 ASR 出错时的兜底价值

输入 `リンファンは手の中の声堂の鍵を強く握りしめ。`（"声堂"是识别错误）：

| 配置 | 译文 |
|---|---|
| **有术语表** `{リンファン:林凡, 声堂:青铜}` | `列车？林凡握着手中青铜钥匙的手紧了紧。` ✅ |
| 无术语表 | `列车？林凡紧紧攥着手中那把钥匙的声音，在掌心发出回响。` ❌ 胡话 |

**结论**：术语表不只是统一译名，它还能把 ASR 的同音字错误拉回正确含义。
另外加术语表后模型能自动把 `リンファン` 认成「林凡」（Bing 网页版不填术语表也能做到）。

## 8. 免 key 的网页版通道（实测可用性）

| 通道 | 实测 | 延迟 | 说明 |
|---|---|---|---|
| **Google gtx 端点** | ✅ 可用 | 248~634ms | 无 key 无浏览器，130+ 语言；**必须代理** |
| **Bing ttranslatev3** | ✅ 可用 | ~1235ms | 需 IG/IID/key/token 四件套；**必须代理** |
| 百度 v2transapi | ❌ | — | 需 JS 算的 sign；token/gtk 由风控接口运行时下发 |
| 有道老接口 | ❌ | — | 已改版需签名 |

Bing 参数要求（踩坑记录）：`POST /ttranslatev3?isVertical=1&IG=<IG>&IID=<IID>`，
body 需要 `fromLang/to/text/key/token`，四个值都从 `GET /translator` 页面里抠。
**只给 token 不给 key 会返回 `statusCode:205`。**

可持续性：0.5 QPS（每 2 秒一次）下连打 8 条**零失败**，中位 1235ms ——
可作为实时字幕主力通道之一，但**别调高 QPS**（密集请求会触发 401）。

**关于"要不要用无头浏览器"**：不需要。百度/有道要的是"能跑 JS"而非整个浏览器
（几 MB 的 JS 引擎就够），且真正的成本是维护而非技术。详见
`app/translate/traditional/web.py` 的调研结论。

## 思考（reasoning）必须默认关掉（2026-09 复查）

用户问："访问 OpenAI 兼容接口时，是不是应该默认关闭思考？"

**答案：应该，而且光发一个参数不够。** 字幕翻译是"短句、要快、要省钱"，
思考只会更慢更贵；更糟的是推理模型常把 ``max_tokens`` 全烧在 ``reasoning_content`` 上，
``content`` 返回空串 —— 用户看到的就是**空白字幕**。

### 发了什么（按服务端类型自动选）

| 服务端 | 关思考参数 | 依据 |
|---|---|---|
| vLLM / LM Studio / llama.cpp / 自建 Qwen 兼容 | ``chat_template_kwargs: {"enable_thinking": false}`` | Qwen 系 chat 模板的标准开关 |
| OpenAI 官方（gpt-5 / o 系列） | ``reasoning_effort: "minimal"`` | 官方没有 enable_thinking，只有思考档位 |
| OpenRouter | ``reasoning: {"enabled": false}`` | OpenRouter 的推理控制字段 |
| 阿里 DashScope（OpenAI 兼容） | 顶层 ``enable_thinking: false`` | DashScope 文档 |

配置项：``translate.llm.disable_thinking``（默认 **True**），设置 → 翻译 里有
「关闭思考（推荐）」勾选框。

### 三层兜底（只发参数是不够的）

1. **400 自动降级**：严格网关（OpenAI / DeepSeek 官方）对未知字段会直接 400。
   实测过 LM Studio 接受全部这些字段（逐个试 200 OK），但不能指望所有服务端都宽容，
   所以遇到 400 会自动**去掉这些参数重试一次** —— 宁可关不掉思考，也不能一句都翻不出来。
2. **``/no_think`` 软开关**：空译文 + 服务端回了思考内容时，把 ``/no_think``
   追加到最后一条 user 消息末尾再试一次（Qwen 系软开关，实测部分模型认它）。
   成功则记进 ``note``（"已用 /no_think 关掉思考"）。
3. **内联思考剥离**：有的网关（或开了 reasoning 透传的 llama.cpp）把
   ``<think>…</think>`` 直接塞进 ``content``。不剥掉的话，模型的自言自语会被当成译文上屏。
   现在闭合块与**被截断的未闭合块**都会被丢掉（后者整段丢弃，因为那本来就是思考）。

### 怎么自己验证服务端有没有关掉思考

设置 → 翻译 → 「测试当前翻译通道」现在**真的翻一句**（不再是只 ping 端口），并报告：

```
✅ 大模型：0.4s 译出「他坐在夜晚的列车上，静静地读着书。」（已确认没有思考内容 ✓）
⚠️ 服务端仍然返回了 137 字思考内容——说明这个服务端不吃关思考参数（译文本身没问题，但会慢一些）。
❌ 大模型：12.3s 只回了 842 字思考、没有译文。这是典型的「思考吃光预算」：把「关闭思考」勾上，或换个小一点的模型。
```

实现上是给翻译器加了 ``reasoning_chars_seen`` 计数器（无论有没有译文都统计），
所以这不是"我们请求里写了就当作生效了"，而是**以服务端实际返回为准**。

### 本机实测（LM Studio 0.x + sakura-galtransl-7b）

| 请求 | 结果 |
|---|---|
| 基线（不加任何参数） | 200，13 tokens，译文正常 |
| ``chat_template_kwargs.enable_thinking=false`` | 200，同样结果（服务端接受该字段） |
| ``reasoning_effort=none`` / ``minimal`` | 200（不受支持的值也不会 400，会被忽略） |
| ``reasoning={"enabled": false}`` | 200 |
| 顶层 ``enable_thinking=false`` / ``think=false`` / ``extra_body`` | 200 |

结论：LM Studio 会**忽略**不认识的字段 → 我们的 payload 是安全的；
真正的兜底是上面那三层（400 降级 / ``/no_think`` / 内联剥离），它们都有单元测试
（``tests/test_translate_thinking.py``，11 项）。
