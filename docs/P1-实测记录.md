## 3. 新发现（原计划未预料，必须写进代码）

### 3.1 ⚠️ `uv` venv 的 `python.exe` 是转发器，PID 不等于真实进程

**现象**：`subprocess.Popen([sys.executable, ...])` 返回 `p.pid = 30572`，
但音频会话属于 **43336**，两者不同。

**根因**：`.venv\Scripts\python.exe` 不是真实解释器，而是 uv 生成的**转发器（launcher）**，
它再拉起真正的解释器子进程。真正执行 `winsound` 播放的是那个子进程，音频会话自然挂在子进程上。

**教训（对主程序有直接影响）**：
> **绝不能假定"我启动/我找到的 PID"就是"音频会话的 PID"。**
> 一律以**音频会话枚举结果**为准（`app/audio/process_list.py`），
> 即：用户在下拉框里选的本来就是会话 PID，这条路是对的；
> 但任何"按进程名自动跟随"的逻辑都必须回到会话列表里核对，不能靠 `psutil` 名字匹配后直接用。

**修复**：验收脚本改为让子进程通过 stdout 上报自己的 `os.getpid()`。

### 3.2 ⚠️ 多进程应用：音频会话 PID ≠ 主程序 PID

**现象**：对浏览器 `msedge.exe` 做采集，峰值幅度 **0.000000**（整整 3 秒纯静音）。
而音频会话显示活跃的是 `pid=23784`，我抓的是另一个 `msedge.exe` 子进程 `pid=9264`。

**根因**：浏览器（Chrome/Edge）、Electron 应用（大量小说阅读器、音乐客户端都是 Electron）
有几十个子进程，**只有负责音频渲染的那个子进程**持有会话。

**教训**：
> 对这类应用，"选择进程名"是不够的，必须**列出音频会话**让用户选；
> 并且 UI 上应把多个同名进程明确区分开（这也是为什么
> `process_list.py` 会解析窗口标题、并把 `session_count` 一起返回）。

### 3.3 ⚠️ 目标未播声时，拿到的是「静音流」而不是「无数据」

**现象**：msedge 那个非音频子进程采集 3 秒，`read()` 被调用 300 次、
**每次都有数据返回**（共 1,152,000 字节，速率精确 384 KB/s = 48k×2ch×4B），
但幅度恒为 0。

**教训**：
> 不能靠"有没有数据"判断目标是否在放音——**数据永远有**。
> 必须靠 **VAD / 能量阈值** 判断，并且要用**静音超时**来做"目标已停止播放"的提示。
> 同时也说明：`read()` 的超时不能用来检测进程存活。

### 3.4 格式与分块（修正官方文档）

| 项目 | 实测值 | 官方 README |
|---|---|---|
| 采样率 | **48000 Hz** | 表里写 48kHz，WAV 示例却写 44.1kHz（**示例是错的**） |
| 声道 | **2** | 2 |
| 样本格式 | **float32**（32 bit） | float32 |
| 每次 `read()` 返回 | **480 帧 = 10 ms** | 未说明 |
| 数据速率 | 精确 **384,000 B/s** | 未说明 |

→ WAV 落盘时必须自行转 int16（官方示例的 `setframerate(44100)` 是错的，照抄会产生变速音频）。

### 3.5 `is_process_specific()` 未暴露

`proctap._native.ProcessLoopback` 有 `is_process_specific()`，
但 Python 层 `ProcessAudioCapture` **没有暴露**它。
本实验通过频谱间接证明隔离生效（0.00% 干扰），无需该接口。

## 6. 音频管线标定（app/audio/pipeline.py 实现依据）

### 6.1 ⚠️ 流式重采样有固定缓冲延迟，不是"来一块出一块"

`soxr.ResampleStream` 内部有滤波器缓冲，**输入不足时输出为空**。实测（48k→16k 单声道）：

| 质量档 | 首次出数据的时机 | 折合延迟 |
|---|---|---|
| `QQ` | 第 1 块（10 ms） | 10 ms |
| `LQ` | 第 3 块（30 ms） | 30 ms |
| `MQ` | 第 4 块（40 ms） | 40 ms |
| **`HQ`（默认）** | **第 4 块（40 ms）** | **40 ms** |
| `VHQ` | 第 8 块（80 ms） | 80 ms |

进一步实测 HQ 的输出节奏：第 4 块吐 490 个样本，之后**每 3 块吐一批约 490 个样本**，
即输出是**突发式**的，不是均匀的。

**结论与对策**：
- 这是延迟预算里必须计入的 **40 ms 固定延迟**，不是 bug，不能"修掉"。
- 下游必须有缓冲（已用 `RingBuffer`），不能假设回调每次都有数据、也不能假设节奏均匀。
- `MQ` 与 `HQ` 延迟相同，因此**保留 HQ**（抗混叠质量更好，有利于 ASR 准确率）。
- 长期看总输出量精确收敛到 1/3，**缓冲只带来延迟，不丢数据**（已有回归测试）。

### 6.2 采集启动延迟约 0.6 s

从 `CaptureWorker.start()` 到第一块数据，实测约 **0.6 秒**。构成：
音频会话枚举（pycaw + psutil）+ WASAPI `ActivateAudioInterfaceAsync` 激活。

**后果**：`--record N` 若按墙钟计 N 秒，用户只能拿到约 `N - 0.6 - 0.04` 秒音频
（实测请求 3 秒只得到 2.39 秒）。
**修正**：`record_to_wav()` 改为**按已收样本数计时**（录够 N 秒音频为止），
修正后请求 3 秒精确得到 48000 帧 = 3.00 秒。

### 6.3 端到端保真性结果

`scripts/verify_capture_e2e.py` 实测（注入 660 Hz / 幅度 0.4）：

| 指标 | 期望 | 实测 |
