# 浏览器标签页音频（精确到标签页）

> 目标：**只听某一个标签页**，而不是整个浏览器。
> 结论先行：**操作系统层没有"标签页"这个边界**，所以只能从浏览器内部下手。
> 落地方式是「一个很小的浏览器扩展 + 本机回环 WebSocket」，音频进的是**现有同一条**
> `AudioPipeline`，识别/翻译/字幕链路一行没改。

实测环境：Windows / Edge **153.0.4234.21** / 本机回环
实测脚本：`scripts/probe_audio_sessions.py`、`probe_browser_tabs.py`、
`probe_tab_isolation.py`、`probe_tab_mute_extension.py`、
`probe_extension_transport.py`、`probe_tab_capture_e2e.py`、`cdp_console.py`

---

## 1. 为什么"从外面"拿不到标签页

### 1.1 浏览器实例 = 一个音频会话（实测）

`probe_audio_sessions.py` 不按 PID 合并地枚举音频会话（音量合成器背后那套接口）：

```
    PID  进程                      态  会话标识后 40 位        显示名      窗口标题
  33300  msedge.exe              1  9-4842-a6de-f933b484e886}|#%b{…              
  44160  steam.exe               0  …
  15220  GenshinImpact.exe       1  …                                  原神
```

然后起一个临时 Edge 实例、开**两个同时出声**的标签页（441Hz / 883Hz）：

```
① 临时实例只有一个标签页 A 时：msedge 会话数 = 2   ← 你的 Edge 一个 + 临时实例一个
② 两个标签页同时出声时：       msedge 会话数 = 2   ← 临时实例**仍然只有 1 个**
```

**结论**：Chromium 把整个实例的音频混在一个音频服务进程里，
既没有"每标签页一个会话"，`GetSessionIdentifier` 也区分不出标签页。
进程回环（`proc-tap`）更是只有"进程"这个粒度。

所以"不装扩展、不改启动参数，让本程序直接对接网页"在物理上不存在——**没有那个接口**。

### 1.2 那"本体对接"（CDP 注入）为什么也不做

`--remote-debugging-port` 能在页面里注入 JS 抓 `captureStream()`，但：

- Chrome/Edge 136+ **禁止对默认配置文件开**这个端口（否则等于把登录态暴露给任意本地进程），
  只能另开 `user-data-dir` → **丢登录态**；
- 注入要逐页面做，遇到 DRM / 跨域内容音轨会被静音。

定位为极客玩具，不做主线。

## 2. 划出标签页边界的三种做法（与实测判决）

| 做法 | 做法要点 | 实测结果 | 判定 |
|---|---|---|---|
| ① 扩展只做"闸门" | 扩展把**其它标签页静音**，音频照旧走进程回环 | 陪跑标签页静音后从采集里**彻底消失（−170 dB，数字零）**，目标标签页 **+0.0 dB 分毫不动**，取消静音后原样回来、可重复 | 可用，但**有副作用**（听字幕时其它标签页没声音） |
| ② 扩展搬音频 | `chrome.tabCapture` 取目标标签页音频 → PCM 送给本程序 | **本次采用**，端到端 8/8 通过（见第 4 节） | ✅ 主路线：零副作用 |
| ③ 本体 CDP 注入 | 见 1.2 | — | ❌ 否决 |

做法①的实测细节（`probe_tab_isolation.py`，页面用可逆增益模拟"标签页静音"）：

```
归零段 10.5–30.0s：441Hz -170.3 dB，883Hz +0.0 dB
归零段之后 441Hz 恢复：+0.0 dB
```

后来用**真的** `chrome.tabs.update({muted:true})` 复核（`probe_tab_mute_extension.py`）：
883Hz 在 6.0s/14.0s/22.0s 三次精确跳变（正好对应扩展的时间表），441Hz 全程 0.12734 死平。
**注意**：它虽然能干活，但会把别的标签页静音，所以只作为备选。

## 3. 平台规则：必须由用户亲手触发一次

`chrome.tabCapture.getMediaStreamId()` 的门槛写在 Chromium 源码里
（`chrome/browser/extensions/api/tab_capture/tab_capture_api.cc`）：

```cpp
  // Make sure either we have been granted permission to capture through an
  // extension icon click or our extension is allowlisted.
  if (!extension()->permissions_data()->HasAPIPermissionForTab(
          sessions::SessionTabHelper::IdForTab(target_contents).id(),
          mojom::APIPermissionID::kTabCaptureForTab) &&
      (GetAllowlistedExtensionID() != extension_id)) {
    return RespondNow(Error(kGrantError));
  }
```

要点三条：

1. **授权是按标签页给的**（`kTabCaptureForTab`），来源是"用户在该标签页上点扩展图标"
   （或按 action 快捷键）；
2. 没触发过就是这条错误（本程序会原样转给用户）：
   `Extension has not been invoked for the current page (see activeTab permission). Chrome pages cannot be captured.`
3. `targetTabId` 本身可以指定**任意**标签页，MV3 下也从 Service Worker 调用即可
   （不需要"有页面的调用方"）——**唯一的门就是那一次用户触发**。

所以本程序的产品流程只能是：

```
主窗口选「浏览器标签页」→ 开始字幕 → 在浏览器里切到目标标签页 → 点扩展图标 / 按 Ctrl+Shift+U
```

扩展侧做了两件事让这一步只点一次：

- 本程序请求过采集但还没授权时，会记一个 `pending` 标记；
  用户点开扩展弹窗（= 刚完成一次触发）时，弹窗**自动开始**当前标签页，
  不用再点第二个按钮；
- 弹窗里会说明：**授权只对"点开扩展时所在的那个标签页"有效**，换标签页要再触发一次。

> 自动化测试里没有"人手"，因此 `scripts/probe_tab_capture_e2e.py` 第二遍启动时
> 用了同一个源码里的官方旁路开关 `--allowlisted-extension-id=<扩展ID>`。
> 真实用户**不需要也不该**用它。

## 4. 端到端实测（真实 Edge + 真实扩展）

命令：

```powershell
.venv\Scripts\python.exe scripts\probe_tab_capture_e2e.py
```

它同时做两路采集做对照：

- **A 路**：扩展送来的标签页音频（本程序的 `TabAudioServer`）
- **B 路**：整个 `msedge` 进程回环（现有 `CaptureWorker`，代表"用户实际听到的"）

页面：目标页 441Hz、陪跑页 883Hz，**都在正常出声**（测试音刻意压到 −44 dBFS，
只需要频谱可辨，不吵人）。

结果：

```
服务端计数：收帧=314 收字节=2411520 输出样本=100314（6.3s 音频，16k 单声道）
标签页通道：441Hz=0.00273  883Hz=0.00000
整个浏览器：441Hz=0.00300  883Hz=0.00288

✅ 扩展能连上本程序并完成握手
✅ 能从 Origin 识别出扩展 ID
✅ 放行后扩展真的开始送音频
✅ 目标标签页 441Hz 送到了本程序（0.00273 vs 陪跑 0.00000）
✅ 陪跑标签页 883Hz **没有**混进来（0.00000）
✅ 陪跑标签页照常出声、未被影响（0.00288 vs 0.00300）
✅ 目标标签页回放正常（tabCapture 没把声音吞掉）（0.00300）
✅ 目标回放全程未间断（0.0025 / 0.0026）
结果：8/8 项通过
```

三件事同时被证明：

1. **标签页级隔离**：只有目标标签页的频率进来（陪跑那路是 0）；
2. **零副作用**：陪跑标签页在浏览器里照常有声（0.00288）；
3. **不破坏用户听感**：`tabCapture` 会把标签页音频从默认输出"摘走"，
   扩展把它接回了扬声器，所以浏览器混音里 441Hz 全程都在且不掉电平。

## 5. 架构

```
浏览器标签页
   │  chrome.tabCapture（只有浏览器内部能拿到标签页边界）
   ▼
offscreen 文档（扩展里唯一能跑 Web Audio 的地方）
   ├─ 一路接回扬声器  ← 不做这一步用户就听不见了
   └─ 一路给 AudioWorklet → 20ms/块的 float32 交错 PCM
          │  自己的 WebSocket（role=audio）
          ▼
   ws://127.0.0.1:38991/lst/tab  ← 本程序 app/audio/ws.py（纯标准库实现）
          │
          ▼
   AudioPipeline（48k/立体声/float32 → 16k 单声道）
          │
          ▼
   VAD → 语言路由 → ASR → 翻译 → 悬浮字幕      ← 这一段与进程模式**完全共用**

扩展 Service Worker ── 另一条 WebSocket（role=control）──► 指令与状态
```

**为什么音频不走 Service Worker 转发**：实测 PCM 走 `chrome.runtime` 端口的
`ArrayBuffer` 那一跳会变成 `null`，于是 `ws.send(null)` 发出去的是字符串
`"[object Object]"`，程序侧只看到"无法解析的控制消息"、一个字节音频都收不到。
直连还顺带省掉一次拷贝、少一层延迟。

**为什么本机回环不用第三方库**：协议两端都由我们掌控，只需要"单/双客户端 +
文本/二进制 + ping/pong/close"。`app/audio/ws.py` 是纯标准库实现（`websockets`
等依赖一个都没加），`app/audio/ws_client.py` 是配套的极简客户端（单测、模拟扩展、
自检共用）。

### 协议

| 方向 | 消息 |
|---|---|
| 扩展 → 程序 | `{"type":"hello","protocol":1,"role":"control\|audio","token":"…","format":{"rate":48000,"channels":2,"dtype":"float32"},"tab":{"id":12,"title":"…","url":"…"},"browser":{"name":"Edge"},"capturing":true}` |
| 程序 → 扩展 | `{"type":"welcome","protocol":1,"ok":true,"role":"audio","format":{…},"out_rate":16000}` |
| 程序 → 扩展 | `{"type":"capture","tabId":12,"format":{…}}` / `{"type":"stop"}` / `{"type":"state"}` |
| 扩展 → 程序 | `{"type":"status","tab":{…},"capturing":true}` / `{"type":"error","code":"gesture","message":"…","hint":"…"}` / `{"type":"log","message":"…"}` |
| 扩展 → 程序 | **二进制帧**：裸 PCM（交错、小端、float32、默认 48k 立体声） |

两条连接按角色管理：同角色的新连接替换旧连接（关闭码 `4001`），
不同角色互不影响。只有 `audio`/`both` 角色能改格式（PCM 是从它来的）。

## 6. 安装（用户手册）

1. 地址栏打开 `edge://extensions`（Chrome 是 `chrome://extensions`），
   打开左下角「**开发人员模式**」；
2. 点「**加载解压缩的扩展**」，选中本仓库的 `browser_extension` 文件夹；
3. 回到本程序，主窗口选「**浏览器标签页（只听某一个标签页）**」→「开始字幕」；
4. 在浏览器里切到你要字幕的那个标签页，点工具栏里的扩展图标
   （或按 **Ctrl+Shift+U**）。

主窗口里的「扩展与安装说明…」按钮有同样的步骤，并能一键打开扩展目录 /
复制 `edge://extensions`。

- 端口默认 `38991`；改端口在 **设置 → 网络 → 浏览器标签页通道**，
  同时要在扩展弹窗的「高级」里填一样的。
- 「配对码」留空即不校验（只连本机 127.0.0.1；不校验时本机任何程序都能连上来说
  自己是扩展，影响仅限于字幕内容被伪造）。多人共用电脑时建议填一个。

## 7. 排错
| 现象 | 原因 / 处理 |
|---|---|
| 控制窗一直显示"等待浏览器扩展连接…" | 扩展没装好（`edge://extensions` 里看有没有报错）；或端口不一致 |
| 提示"浏览器要求先由你触发一次" | 正常的安全策略：在该标签页点一下扩展图标，或按 Ctrl+Shift+U |
| 提示"授权只对点开扩展时所在的那个标签页有效" | 你要字幕的标签页不是当前活动页。切过去再触发一次 |
| 目标标签页**本身是静音**的 | 采到的是静音：把标签页自己的静音取消 |
| 点开始后报"端口 38991 被占用" | 换端口（设置 → 网络），并把扩展里的端口改成一样 |
| 扩展报告"创建 offscreen 文档失败" | 扩展刚被重新加载过，等 2 秒再点一次；或到 `edge://extensions` 点"重新加载" |
| 扩展报告"与本程序失联过久，停止采集" | 字幕程序被关掉了。重开字幕程序后重新触发一次 |

排错利器（都在 `scripts/` 下，任意时刻可复现现场）：

```powershell
# 1) 看当前音频会话（判断"到底几个会话"）
.venv\Scripts\python.exe scripts\probe_audio_sessions.py

# 2) 看扩展各页面/Service Worker 的控制台（CDP，含看不见的 offscreen 文档）
.venv\Scripts\python.exe scripts\probe_extension_console.py

# 3) 完整端到端（起临时 Edge、加载扩展、频谱对照）
.venv\Scripts\python.exe scripts\probe_tab_capture_e2e.py
```

## 8. 踩过的坑（留给以后维护的人）
1. **`chrome.runtime.onConnect` 在 offscreen 文档里永远不会触发**。
   它只在"有别人连进来"时触发，而 offscreen 文档永远只是主动 `connect()` 的那一方。
   监听必须挂在自己 `connect()` 出来的那个 port 上——否则 SW 发来的 `start` 石沉大海，
   表现为"等待 offscreen 响应超时"。
2. **`ArrayBuffer` 经 `chrome.runtime` 端口转发会变 `null`**（见第 5 节）。
   音频不要走扩展端口转发。
3. **Service Worker 的连接状态机不能想当然**。曾经因为
   ① `connect()` 是异步的、启动时被三处并发调用；② `onclose` 里无条件 `ws = null`，
   导致"新连接顶掉旧连接 → 旧连接的 onclose 又触发重连 → 再顶掉"，
   **每秒互相踢一次、永远握不上手**（服务端日志里全是 `code=4001`）。
   修法：`connecting` 标志 + `if (ws === sock) ws = null` + 统一的 bootstrap。
4. **`chrome.commands` 的 `suggested_key` 可能被拒绝**（本机实测两个组合的
   `shortcut` 都是空字符串）。扩展会把 `chrome.commands.getAll()` 的结果上报，
   别猜。
5. **offscreen 文档里的 `AudioContext` 可能是 `suspended`**（自动播放策略）。
   那时 worklet 一次都不会被驱动，表现是"扩展说开始采集了，程序收不到音频"。
   扩展会检查 `ctx.state !== "running"` 并直接报错，而不是静默失败。
6. **`chrome.tabCapture` 会把标签页音频从默认输出摘走**。不把它接回
   `ctx.destination`，用户就听不见了（这是最容易忘、后果最严重的一步）。
7. **可能同时有多个扩展实例连同一个端口**（实测：用户日常浏览器里装了一份，
   临时跑测试的浏览器又装了一份）。早期的实现因此踩了两个雷：
   ① 任何控制连接的 hello 都会覆盖 `capturing`，于是一个**没在采集**的实例
   把正在进行的采集说成"没在采集"，界面上看起来就是"音频发送暂停了"；
   ② 连接数上限 2 + "最旧先踢"的淘汰策略，让新来的控制连接把**正在送音频的那条**
   踢掉（音频真的断了一下）。
   现在的规则：**正在送音频的那条说了算**；跨源的连接不许顶掉正在工作的连接
   （会被明确拒绝并在界面上说明原因）；淘汰优先踢"还没握手的"。
8. **同一角色的旧连接要立刻从登记表摘掉**（`WSServer.drop_client`）。
   否则"状态里挂着死连接"，后面的淘汰判断会拿它当活人，把真干活的挤掉。
9. **`role` 字段是后加的**：旧版扩展的 hello 没有它。旧版连接一律**并存**
   （不按角色替换），否则它的 SW 与 offscreen 会互相顶成死循环。
   检测到旧版时程序会提示「请在 edge://extensions 里点【重新加载】」——
   **改完扩展代码一定要在 `edge://extensions` 重新加载**，unpacked 扩展才会生效。
10. **音轨会在目标标签页"不再出声"时结束**（视频播完/暂停/换曲）。
    早期实现收到 `ended` 就直接停止采集，用户必须再点一次扩展图标；
    现在会自动重试 `startCapture(同一标签页)`（授权还在，不用用户再点），
    失败三次才提示用户手动触发。

## 9. 三个真实现场的回归验证（2026-09-13）

用户实测反馈："**新建一个播放音频的标签页**，原本正在进行的音频发送会暂停，
还得手动再点一次。" 顺着这条线查出了三个真问题，都修了，并留下可复跑的验证脚本：

```powershell
.venv\Scripts\python.exe scripts\probe_tab_new_tab_interrupt.py
```

它一次跑三个现场，8 项全通过（最近一次实测）：

| 现场 | 做法 | 实测结果 |
|---|---|---|
| A 新建出声标签页 | 采集进行中再开一个 883Hz 的标签页 | 新增 **401 帧/8 秒**（50 帧/秒），`capturing` 仍为真，目标标题没被覆盖 |
| C 另一个浏览器也装了扩展 | 从**另一个目录**加载同一个扩展（扩展 ID 不同），另起一个 Edge | 服务端明确拒绝并提示「已有另一个浏览器扩展在当 control，本条连接被忽略」，我们的音频**没有被挤断**（751 帧） |
| B 音轨结束 | 先停采集，再调用扩展的自动恢复 | 控制台可见 `已停止采集 simulated-ended` → `开始采集 tab=…` → `音频通道已连上`，**恢复后新增 73 帧，无需手动再点** |

排查过程中还有两个"顺手修"的东西：

- **离线算扩展 ID**（`scripts/ext_id.py`）：算法是对扩展目录绝对路径按 **UTF-16LE**
  取 SHA-256、前 16 字节、每个半字节映射到 `a`–`p`
  （实测与 CDP 里看到的 ID 完全一致）。自动化测试要用
  `--allowlisted-extension-id=<ID>`，以前只能"先启动一遍再读出来"。
- **`scripts/probe_tab_capture_e2e.py`** 现在默认不再跑"先复现浏览器拒绝"那一遍
  （慢一倍），需要时加 `--show-gesture-rejection`。

## 10. 已知限制
- 同时开**多个浏览器配置/实例**且都在出声时，只能选其中一个（本程序按扩展连上来的那条通道为准）；
- 扩展要**侧载**（开发人员模式）。我们没上架商店，因为这不是通用工具；
- 首次/换标签页都必须由用户**亲手触发一次**（平台规则，见第 3 节）；
- 只测过 Edge/Chromium 系；Firefox 没有同名 API，不在支持范围；
- DRM（Widevine）内容未实测（tabCapture 取的是解码后的音频流，理论上可用，但没有验证过）。
