## 2. ⚠️ 发现并推翻的错误假设：ProcTap 的 `--list-audio-procs` 不可用

**计划书初稿的假设**：`proctap --list-audio-procs` 等价于"音量合成器里正在发声的程序列表"，
可以直接作为 UI 下拉框的数据源。

**实测结论：这个假设是错的。**

查阅已安装源码 `.venv/Lib/site-packages/proctap/__main__.py` 第 61–160 行：

- Windows 分支的注释虽写着 "Uses Windows Audio Session API to detect active audio sessions"，
  但**实际实现**是调用 PowerShell 执行：

  ```powershell
  Get-Process | Where-Object {
      $_.MainWindowHandle -ne 0 -and $_.ProcessName -match 'audio|media|music|video|player|chrome|firefox|edge|spotify|discord|teams|zoom|vlc|winamp|foobar|aimp'
  }
  ```

  即**按进程名正则匹配关键词**，与音频会话毫无关系。

- 另一个分支更粗糙：列出"有窗口的进程"再按关键词字符串过滤，并自己承认
  "This shows processes that might be playing audio based on process names"。

- 整个 `proctap` 包的 Python 层**没有任何音频会话（IAudioSessionManager2）相关调用**。
  `_native.pyi` 暴露的 `ProcessLoopback` 只有 `start/stop/read/get_format/is_process_specific/get_last_error`。

**影响**：`app/audio/process_list.py` 必须**自行实现**枚举，不能依赖 proc-tap。

**采用的替代方案**：`pycaw`（Python Audio Control Library，20251023）
→ `AudioUtilities.GetAllSessions()`，底层就是音量合成器使用的
`IAudioSessionManager2` / `IAudioSessionEnumerator`。

## 3. pycaw 实测行为

```
AudioUtilities.GetAllSessions()   # 无参数，返回默认播放设备上的会话列表
```

会话对象可用字段（实测）：

| 字段 | 说明 |
|---|---|
| `ProcessId` | 进程 PID；**系统声音会话 PID = 0**，且 `Process` 为 `None` |
| `State` | `0=Inactive`、`1=Active`、`2=Expired`（WASAPI `AUDIO_SESSION_STATE`） |
| `Process` | `psutil.Process` 实例，可 `.name()` / `.exe()` |
| `DisplayName` | 多为空串；系统声音为资源串 `@%SystemRoot%\System32\AudioSrv.Dll,-202` |
| `Identifier` | 含设备 GUID + 可执行文件路径 + 会话 GUID |

**不存在的字段（踩坑）**：
- `pycaw.pycaw` **没有** `AudioSessionState` 枚举类（初稿误用了它）→ 直接用整数常量。
- `AudioSession` **没有** `IsSystemSoundsSession` 属性 → 用 `ProcessId == 0` 判定系统声音。

**实测输出**（本机真实抓取）：

```
pid=29384  state=0 (Inactive)  steam.exe
pid=43052  state=1 (Active)    GenshinImpact.exe   ← 正在放音
pid=23784  state=1 (Active)    msedge.exe          ← 正在放音
pid=0      state=0 (Inactive)  系统声音
```

**边界**：`GetAllSessions()` 只覆盖**默认播放设备**。若目标程序输出到非默认设备，
需要遍历 `AudioUtilities.GetAllDevices()` + `GetAudioSessionManager(dev)`。
代码已保留 `all_devices=True` 分支（P1 完善并实测）。

## 4. proc-tap 实测 API（与 README 不符之处）

| README 写的 | 实际存在的 |
|---|---|
| `from proctap import ProcTap, StreamConfig` | ❌ 不存在 |
| — | ✅ `from proctap import ProcessAudioCapture` |

`ProcessAudioCapture` 实测签名：

```
__init__ / start() / stop() / close() / __enter__ / __exit__
is_running (property) / pid (property) / format (property)
set_callback(callback) / get_format() / read(timeout=1.0)
```

常量：`STANDARD_SAMPLE_RATE`、`STANDARD_CHANNELS`、`STANDARD_FORMAT`、`STANDARD_SAMPLE_WIDTH`。

⚠️ 官方 README 自相矛盾：格式表写 **48 kHz / 2ch / float32**，
但 "Save to WAV" 示例注释写 **44.1 kHz**、`setframerate(44100)`。
**P1 必须用 `get_format()` 实测确认，不能信文档。**

底层原生模块 `proctap._native.ProcessLoopback` 使用
`ActivateAudioInterfaceAsync` 做进程级回环，支持
`is_process_specific()` 查询"是否真的抓的是指定进程"（还是退化成系统回环）——
**P1 必须检查这个返回值**，否则会静默抓到全部系统声音。
