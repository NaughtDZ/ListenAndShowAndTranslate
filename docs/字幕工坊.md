# 字幕工坊（离线转写）

> **打开方式**（三选一）：
> - 双击 **`字幕工坊.bat`** —— 不用重新打包，装了环境就能用（黑框一闪即过）
> - 双击 **`听显译-字幕工坊.exe`** —— 跑过 `构建exe.bat` 后就有，完全没有黑框
> - 命令行 `python main.py --studio`（想盯着报错看就用 `启动.bat --studio`）
>
> 代码：`app/offline/`（内核）+ `app/ui/studio.py`（界面）
> 测试：`tests/test_offline_subs.py`
> 独立入口：`字幕工坊.bat`、`frontend_studio.py`（→ `听显译-字幕工坊.exe`）

---

## 1. 它是什么

把**音视频文件**离线转写成字幕文件，可选再调 LLM 翻译：

```
拖入文件/文件夹 → VAD 切句 → 每句整句识别 →（可选翻译）→ 切行 → 导出 srt/vtt/lrc
```

和实时字幕（悬浮窗）的关系：**引擎、模型、翻译通道全部复用**，只是工作流不同——
离线没有"未来"压力，所以不做流式，每句都用最准的模型整句识别。

---

## 2. 为什么它比实时字幕更准

实时场景被迫取舍（延迟 vs 质量）；离线可以等，所以：

| | 实时 | 离线 |
|---|---|---|
| 断句静音 | 350ms（要跟手） | 500ms（句子更完整，翻译上下文更好） |
| 识别方式 | 流式 partial 或分块 | 一律整句 |
| 紧张程度 | 必须比实时快 | 慢点无所谓 |

---

## 3. 输入格式

**有 ffmpeg**：几乎全部——mp3 / m4a / aac / wav / flac / ogg / opus / **mp4 / mkv / mov / webm**（自动抽第一条音轨）。

**没有 ffmpeg**：退回 `soundfile`，只支持 wav / flac / ogg / **mp3** / aiff / caf / w64。
拖 m4a 或视频会明确报"装 ffmpeg 后即可处理"，不会静默失败。

> 本机实测：`libsndfile 1.2.2` 已经能读 mp3，但**不支持 m4a/aac/mp4/mkv**。
> 界面上没检测到 ffmpeg 时会直接提示一次。

## 4. 参数

| 参数 | 作用 | 建议 |
|---|---|---|
| 识别模型 | 只列**离线分块**模型（SenseVoice / Parakeet-ja / Dolphin / Whisper…） | 日语选 SenseVoice；动画/galgame 可选领域微调模型 |
| 音频语言 | 设对语言更准；`auto` 走模型自带语种识别 | 知道就选 |
| VAD 模型 | 默认 Silero；**轻声/耳语选 Whisper-VAD ASMR** | 见 `docs/耳语VAD.md` |
| 断句静音 | 静多久算一句说完 | **800ms 起步**；分句还是碎就往上调（1200 实测最佳），字幕长得离谱就往下调 |
| 最短语音 | 短于此的段丢弃（滤咳嗽/键盘声） | 250ms |
| 最长成句 | 一直不停说时强制断句 | **8s，别调大**（见第 6 节坑 2） |
| 每行字数 | 一行最多多少全角字；0=不切 | 24；LRC 必须切 |
| 字幕格式 | srt / vtt / lrc 可多选 | SRT 最通用 |
| 输出内容 | 原文 / 双语 / 只要译文 | 双语需要开翻译 |
| 翻译 | 勾「调用 LLM 翻译字幕」，再点旁边的 **「翻译设置…」** 配通道（LLM 或传统 API） | 没配好时那一行会标红；开跑前还会再提醒一次 |
| 输出目录 | 留空 = 与源文件同目录 | — |

文件名规则：原文 `a.srt`；双语/译文 `a.zh.srt`（不覆盖原文）。

### 翻译的「单次预算」

设置 → 翻译 → 大模型设置 → **单次预算**。它决定"一次请求塞多少内容"，
不是"翻不翻"：

| 档位 | 适合 | 短字幕（20 字/条） | 前文行数 |
|---|---|---|---|
| **4k** | 8G 显存 / 8k 窗口 | 160 条/批 | 28 行 |
| **8k** | 12~16G 显存 | 371 条/批 | 57 行 |
| **16k** | 24G+（4090/5090） | 撞 400 条上限 | 115 行 |
| **32k** | 云端 32k 窗口 | 撞 400 条上限 | 230 行 |
| 不限 | 仅兼容老配置 | 回到"固定 8 条一批 + 固定 20 行前文" | 20 行 |

> ⚠️ **预算不是全部给正文的**：提示词（约 665 token）+ 前文（预算的 1/3）
> 要先扣掉，剩下的才装原文。所以 4k 档实际只有约 2k token 装内容——
> 这是**故意的**：少装一点，总比"超了模型上下文窗口、整批翻译失败"强。
> 如果模型窗口富余（LM Studio 里 context 设了 32k），把预算调大一档更划算。

两个要点：

1. **输出上限自动算**（约输入的 0.8 倍），不用另调。以前写死 512 ——
   8 条一批勉强够，一批几十条时译文必被截断。
2. **短字幕会先撞"400 条/批"的上限**，所以 16k 和 32k 对短字幕没区别；
   预算的收益在**长字幕**（每条 50~100 字）和**前文**上更明显。

> 为什么不让它一口气翻完整个文件：一部电影 800~1500 条，输出要 2~3 万 token，
> 超过绝大多数模型的单次生成上限，会静默截断。真要"一把梭"，用 32k 预算 +
> 短文件（< 400 条）才现实。

> **预算必须明显小于模型的上下文窗口**。程序没法知道你在 LM Studio 里设了
> 多少 context——设 4096 时用 4k 预算会贴着上限跑，建议留一倍余量。

### 「边翻译边总结专名」

设置 → 翻译 → 大模型设置 → **边翻译边总结专名**（默认开，只对 LLM 通道有效）。

长片切成很多批之后，前面出现的人名一旦滚出前文，后面就可能换个译法——
同一个角色一会儿「林凡」一会儿「林繁」。勾上后会在**本次任务内**建一张临时专名表：

```
已识别的原文
   ↓  程序统计（n-gram / 字符类规则，零 token）
候选词：リンファン、青銅、駅前
   ↓  问模型一次「这些该译成什么」
临时表：リンファン→林凡、青銅→青铜、駅前→车站前
   ↓  注入后续每一批（用户手填的术语表优先）
```

**为什么是两次调用而不是"翻译时顺带输出"**：

1. 现在批量输出是「1. 译文」逐行编号。在同一次回答里再塞一段术语表，
   等于给解析器加一条必须容错的岔路——模型写歪一次，整批译文就废了。
   译文是主产物，不该为术语表冒这个险。
2. 候选词由**程序**统计（零 token），只有译名要问模型。每批都问 = 请求数翻倍；
   只在有新候选时问一次，整部片子通常 2~5 次。

**三道闸防「错误译名污染全片」**（项目里踩过"垃圾进上下文带歪后续"的坑）：

| 闸 | 规则 |
|---|---|
| 候选 | 必须在原文出现 ≥3 次；片假名整串抓（不滑窗）、英文大写词组、日语汉字词 |
| 译名 | 长度合理、不含「（人名）」「→」这类解释痕迹、不等于原文 |
| 优先级 | **永不覆盖用户手填的术语表** |

**中文为什么不做自动提取**：汉字没有"片假名=人名"这种字符线索，2~3 字滑窗一定会
切出 `林凡握`、`紧了手`、`林凡低` 这种跨词碎片，而碎片和真名的频次是同一量级、
阈值分不开。灌进去会直接破坏句子。中文请用手填术语表——那里你能一眼看出对错。

**生命周期**：表只活在这次任务里（函数返回即丢弃），不落盘、不进缓存、
不影响下一次任务。日志里会打印「临时术语表（任务结束即丢弃）：…」。

#### 跨文件保持（同一个勾选框下面的选项）

批量处理**同一部剧的多集**时，人名当然应该一样——所以「3. 输出」页还有一个

> ☑ **专名表跨文件保持（整批任务共用，结束才丢）**

| 勾选状态 | 行为 |
|---|---|
| **勾上（默认）** | 整批任务共用一���表：第 1 集学到「リンファン→林凡」，第 2 集直接用，不再重复问模型 |
| 不勾 | 每个文件单独建表，各集之间不共享（适合"一批里混了好几个不相干的片子"） |

无论勾不勾，表都只在**本次任务**内存在：`run()` 返回时丢弃，不落盘。
不勾时只是"每个文件新建一张"，不是"保存到磁盘"。

> 文件太短（不足 5 条已经翻过）时不会建表——候选词要求每个出现 ≥3 次，
> 内容太少统计不出可信的专名。短片本来也不需要跨批一致（一次请求就翻完了）。

日志里能看到当前进度：

```
[1/3] 第一集.mkv · 23:41 · ffmpeg
  · 专名表 +2 条：リンファン→林凡、青銅→青铜
[2/3] 第二集.mkv · 23:38 · ffmpeg
  · 专名表：リンファン→林凡、青銅→青铜、駅前→车站前
...
批次结束，临时专名表丢弃（共 3 条）：リンファン→林凡、青銅→青铜、駅前→车站前
```

## 5. 三种格式的差别

| 格式 | 时间戳 | 结束时间 | 备注 |
|---|---|---|---|
| SRT | `00:00:01,234` | 有 | 最通用，几乎所有播放器/剪辑软件都认 |
| VTT | `00:00:01.234` | 有 | 网页 `<track>` 用，带 `WEBVTT` 头 |
| LRC | `[00:01.23]` | **没有** | 歌词格式，一行 = 一屏，所以必须先切行 |

双语在 LRC 里写成**同一时间戳的两行**（原文一行、译文一行）；
在 SRT/VTT 里是**同一条字幕的两行文本**。

编码统一 **UTF-8 with BOM**（Windows 播放器兼容性最好），换行 LF。

## 6. 两个必须记住的坑

### 区分角色（说话人分离）

「2. 参数」里的 **☐ 区分角色（说话人分离）**，勾上后导出的字幕会带角色前缀：

```
1
00:00:01,574 --> 00:00:03,488
[S1] 日本はちゃんと聞きといてますか。

2
00:00:05,862 --> 00:00:07,872
[S2] 第印象、夜の列車。
```

**它给的是匿名编号，不是角色名**：S1/S2 是聚类出来的，同一文件内稳定
（S1 始终是同一个人），但**跨文件不保证**——第 1 集的 S1 可能是第 2 集的 S2。
要变成「哥哥」「老师」得靠 LLM 从对话内容推断（还没做）。

需要的模型（各约 5.7MB / 27MB，总计约 33MB）：

```
data/models/pyannote-segmentation-3-0/model.onnx
data/models/campplus-sv/campplus.onnx
```

缺模型时会**自动跳过**并提示（识别照常，只是没有角色前缀）。

**为什么不引入 pyannote.audio**：sherpa-onnx 1.13 已经把整套推理内置了
（`OfflineSpeakerDiarization`），不需要 torch——对一个纯 CPU 的桌面程序
这是决定性的。实测 RTF ≈ 0.018，一小时的片子约 65 秒。

**两个代价**：

| 代价 | 说明 |
|---|---|
| 多一遍推理 | 一小时约 65 秒（比 ASR 便宜得多） |
| 内存 | 要把整段音频留住做全局聚类，按 int16 存约 **115MB/小时** |

> 想省内存/时间就别勾；只有在**真的多人在说话**（动画、广播剧、访谈）时才值得开。
> 单人朗读开它没有意义——所有人都分到 S1。

### 坑 1：喂给 VAD 的块必须 ≤250ms
sherpa-onnx 的 `accept_waveform` 对"一次传多长"敏感。同一段 11.4 秒日语音频只改块大小：

| 块大小 | 结果 |
|---|---|
| 100ms | ✅ 正确切成 2 段（0.07~2.19 / 2.89~10.78） |
| 200~250ms | 段边界开始漂移（每段多算 0.1s） |
| **320ms 起** | ❌ 两段被**并成一段**（断句失效） |
| 10 秒 | ❌ 只吐出末尾 1.7 秒，前面的全丢 |

实时管线天然喂 10~20ms 的回环块，所以从没暴露；离线解码是 10 秒一块，**必须再切小**。
代码里由 `app/offline/transcribe.py` 的 `VAD_BLOCK_SECONDS = 0.1` 负责，并有测试守着。

### 坑 2：`最长成句` 不能因为"离线可以等"就调大

VAD 正是靠它给"一直不停地说"强制断句。若它比最长连续语音还长，VAD 会认为
"这一句始终没说完"，整段挂着不产出，直到 flush 才吐出一小截——
实测 11.4s 连续语音、上限设 15s，最终只拿到末尾 1.7s。

所以默认仍是 8s（与实时一致）。

**补充实测（2026-11，SenseVoice + silero）**：把上限从 8s 调到 15s / 30s，
**结果一个字节都没变**——因为 VAD 在句间停顿处就切了，8s 上限根本没被触发。
换句话说：

> **想让句子更长，该调的是「断句静音」，不是「最长成句」。**
> `最长成句` 只是"连续说话不停"时的一道保险丝。

同一批实测里还有两个值得记住的数：

| 切法 | 日语 CER | 现象 |
|---|---|---|
| 上限 2s | 7.5% | `…食べながら。は昨日の出来事を…` —— 主语「彼は」被切掉，译文只能猜 |
| 上限 8s（默认） | **5.7%** | 正常 |
| 整段不切（不做 VAD） | 9.4% | 出现「第 印象」「凛ン ファン」「青堂」等退化 |

结论：**识别层保持现状就是最优**。切碎会丢语义，整段喂会让短句模型退化。
"听完再理解"这件事只能在**翻译层**做——所以才有上面那个「单次预算」。

### 坑 4（2026-11 修）：尾巴几个字被单独切成一段

**症状**：一句话的最后几个字被单独打一个时间点、分到下一段。实测
`real_ja_2.wav` 里 VAD 在「日本語をちゃんと聞き取**れ**」和「**ている**かどうか」
之间切了一刀——后一段只有 **1.19 秒**、间隔 0.41 秒。翻译拿到的是半个谓语，
自然翻不对。

两层修：

1. **碎片合并**（`cue.merge_fragments`，默认开）：短（≤1.2s）+ 紧邻（≤0.6s）
   的段落并回前一句。纯文本拼接，不用重跑识别。
2. **断句静音默认 500 → 800ms**。实测同一段音频：

   | 断句静音 | 结果 |
   |---|---|
   | 500ms | 3 段，其中一句被从动词中间切开 |
   | **800ms** | 3 段，第二句完整 |
   | 1200ms | 2 段，最完整（但快速对话有并句风险） |

离线不用跟手，所以默认值比实时（350ms）大。分句还是碎就调到 1000~1200。

### 坑 3（已处理）：时间戳不能用 `ASREvent`

`ASREvent.audio_start_s/audio_end_s` 填的是"上次出结果 → 本次喂完"，**夹着静音**，
写进字幕会让每句都提前冒出来。离线工具直接用 `SpeechSegment.start_sample`
（VAD 给的真实语音起点）算时间。

## 8. 独立入口与打包

| 入口 | 怎么来的 | 黑窗 |
|---|---|---|
| `字幕工坊.bat` | 仓库自带，装了环境就能用 | 闪一下（用 `pythonw` 启动后立刻关掉） |
| `听显译-字幕工坊.exe` | `构建exe.bat` 打包（PyInstaller onefile） | **完全没有** |
| `python main.py --studio` | 命令行 | 取决于你用哪个解释器 |

两个 exe 的分工（`scripts/build_exe.py` 里的 `TARGETS`）：

| exe | 入口脚本 | 打开什么 |
|---|---|---|
| `听显译.exe` | `frontend.py` | 主程序（实时字幕） |
| `听显译-字幕工坊.exe` | `frontend_studio.py` | 字幕工坊（固定补 `--studio`） |

`frontend_studio.py` 只有几行——真正逻辑仍在 `frontend.py`（找程序目录、检查 `.venv`、
用 `pythonw` 拉起、自己退出），它只是**转发参数并固定加上 `--studio`**。
PyInstaller 的 `--onefile` 不能把"默认参数"塞进 exe，所以想双击即开就得两个入口脚本。

> **独立打开时，翻译通道在哪儿配？** 主设置窗不会自动弹出来，
> 所以在「3. 输出」里放了一个 **「翻译设置…」** 按钮：点它会打开主设置窗并直接
> 落到「翻译」页。上方那行状态会实时告诉你当前通道是什么、有没有配好
> （没配好是红色、并给出这个入口；开跑前还会再拦一次）。
>
> ⚠️ 「通道」的默认值是「不翻译（只显示原文）」。这时大模型那一整块会是
> **禁用**状态——但**仍然显示出来**，并附一句解释和「就用『本地/在线大模型』通道」
> 按钮（以前它被 `setVisible(pid == "llm")` 整个藏掉，用户会以为设置里根本没有 LLM）。
> 选它之后，接口地址 / API Key / 模型名才可填。
